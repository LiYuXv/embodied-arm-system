# ela3_demo 数据集问题分析与修复记录

数据集路径：`lerobot_data/ela3_demo`（LeRobot v3.0 格式，当前 180 episodes / 34190 帧 / 20 fps）

> 历史记录：问题 1~4 在数据集为 80 episodes / 11383 帧时排查修复；后续数据扩充至
> 180 episodes / 34190 帧。**问题 5（action==state 退化）是导致真机推理失败的根因**，
> 于扩充数据上发现并修复。**问题 6（meta 与 data 行不一致）在合并后批量剪辑的工作流中
> 暴露（131 episodes / 90192 帧），于 2026-08-12 修复并加固程序**。
> **问题 7（task_index 非 0 基连续）于 2026-08-13 训练时暴露（124 episodes / 85816 帧），
> 已修复存量数据、根治程序根因（`_batch_rename_task` 并入后压实）并在"数据集检查"中
> 新增第 7 项检测**。

## 背景

首次训练时报错：

```
IndexError: Invalid frame index=190 for streamIndex=0; must be less than 185
```

逐层排查后发现数据集的**元数据与实际文件不一致**，共 4 类问题。根因推测：数据采集后经过裁剪/合并（stats count=26982 > 实际 11383 帧，episode 引用的视频文件编号不连续），但 `meta/` 元数据没有同步更新。

---

## 问题 1：meta/episodes 中的 data 文件映射失效

**现象**：`meta/episodes/chunk-000/file-000.parquet` 中每个 episode 的
`data/chunk_index, data/file_index` 指向 `file-001 ~ file-095`（每 episode 一个文件），
但 `data/chunk-000/` 下实际只有 `file-000 ~ file-011` 共 12 个 parquet
（数据已按 chunks_size=1000 合并，每文件约 1000 行、含多个 episode）。

**后果**：LeRobotDataset 按 meta 找不到数据文件，无法读取样本。

**修复**：扫描全部 12 个 data 文件，按 `episode_index` 列建立 episode → 实际文件映射，
重写 meta 中每个 episode 的 `data/chunk_index`（=0）和 `data/file_index`（=0~11）。

---

## 问题 2：视频 to_timestamp 与实际视频时长不符

**现象**：meta 中 `videos/observation.images.cam{1,2}/to_timestamp` 记录的是**墙钟时长**
（如 ep0：19.85s），但 ffprobe 实测视频时长为 `length/20fps`（ep0：7.35s，147 帧）。
全部 80 个 episode 均不一致。

**后果**：lerobot v3 按时间戳解码视频帧，请求的时间戳超出视频实际时长，导致帧索引越界。

**修复**：将每个 episode 双摄像头的 `to_timestamp` 重写为 `length / fps`（`from_timestamp` 全部为 0，无需修改）。已用 ffprobe 逐文件验证视频帧数 == episode length。

---

## 问题 3：data parquet 中 frame_index / timestamp 列错乱

**现象**：数据行中 `frame_index` 和 `timestamp` 是原始墙钟采样值而非按 20fps 规整的值，
例如 ep0（长度 147）中出现了 `frame_index=385, timestamp=19.25`——超出该 episode 范围。

**后果**：这是报错的**直接原因**。`LeRobotDataset.__getitem__` 用数据行的 `timestamp`
列计算视频查询时间戳（`lerobot_dataset.py:1009-1015`），torchcodec 将 9.5s 映射为
frame 190，而视频只有 185 帧 → `IndexError`。

**修复**：验证全局 `index` 列连续递增、episode 行连续排列后，按行序对每个 episode 重新生成：
- `frame_index` = 0, 1, ..., length-1
- `timestamp` = frame_index / 20

---

## 问题 4：meta/stats.json 统计量基于裁剪前数据

**现象**：stats.json 中 `count=26982`，而实际 `total_frames=11383`，
说明统计量是在裁剪/删除部分 episode 之前计算的。

**后果**：SmolVLA 对 state/action 使用 MEAN_STD 归一化，过期统计量会让归一化分布偏移，
影响训练效果（不致命，但不应使用）。

**修复**：从实际 12 个 data 文件重新聚合 `observation.state`、`action`、`timestamp`、
`frame_index` 的 min/max/mean/std/count/q01~q99，写回 stats.json（count=11383）。
图像统计量未重算（需解码全部视频，且 VISUAL 归一化模式为 IDENTITY，不影响训练）。

---

## 问题 5：action 与 observation.state 完全相同（真机推理失败的根因）

**现象**：SmolVLA 训练后离线推理曲线（`inference_plots/*.png`）与 GT 基本贴合，但全程有
小弧度抖动；上真机后**几乎全失败**，机械臂一卡一卡地运动，且**推理出的路线像被固定在
几条轨迹上，不管场景如何变化都不受影响**。

**根因**：录制程序 `widgets/camera_pyqt.py` 的 `LeRobotRecordThread.run()` 在 `add_frame`
时把**同一个当前位姿 `pose8`** 同时写入了 `observation.state` 和 `action`：

```python
# 旧代码（camera_pyqt.py:236-237）
"observation.state": item["pose8"].astype(np.float32),
"action":            item["pose8"].astype(np.float32),   # 与 state 同一个变量！
```

逐 chunk 检查全部 35 个 data parquet，`max|action − state| = 0.0`（**逐位完全相同**），
180 个 episode 无一例外。于是训练任务退化为“预测当前位姿”。

**证据链**：

1. **数据退化**：全数据集 `action == observation.state`（bit-identical，0 误差）。
2. **模型学会恒等映射、忽略视觉**（对照实验，用 `predict_action_chunk` 每次重新生成）：

   | 实验（episode 0 帧 100 为基准） | 位姿输出最大变化 | 结论 |
   |---|---|---|
   | 换图像、保留 state | 0.0043 | 换场景输出几乎不变 → **视觉被忽略** |
   | 换 state、保留图像 | 0.3116 | 输出完全跟着 state 走 |
   | 输出 vs 输入 state | 0.0042 | 输出 ≈ 当前 state（恒等） |

3. 这完美解释所有现象：
   - 离线曲线贴合 = 假象（action==state，模型输出 state 自然 ≈ GT action）；
   - 真机“路线固定/无视场景” = 模型不看摄像头，只回显当前位姿；
   - “一卡一卡”抖动 = 输出 ≈ 当前位姿 + flow-matching 随机噪声（实测位姿 ~0.004、夹爪 ~1.5°），
     真机上即原地抖、不主动规划；
   - 几乎全失败 = 模型根本没有“朝目标运动”的能力。
4. 上一节提到的推理曲线抖动（chunk 边界随机噪声）只是次要放大因素，**真正让真机失败的是
   这个恒等映射**。

### 5.1 修复存量数据（`fix_action_labels.py`）

在每个 episode 内把 `action` 错位为未来位姿：`action[t] = observation.state[t+1]`
（lookahead=1），末尾帧沿用末帧位姿。脚本特性：

- 自动备份原始 `data/` 与 `meta/stats.json` 到 `.bak_action_fix_<时间戳>/`
- 严格保持原有 `file-000…file-034` 分块，**不破坏** `episodes` 元数据中的
  `data/chunk_index`、`data/file_index` 指针
- 修复后重算 `meta/stats.json` 的 action 统计项
- 支持 `--dry-run` 预览、`--lookahead N`

```bash
python3 fix_action_labels.py --root ./lerobot_data/ela3_demo --lookahead 1 --dry-run  # 预览
python3 fix_action_labels.py --root ./lerobot_data/ela3_demo --lookahead 1            # 执行
```

**修复结果**：

| 校验项 | 修复前 | 修复后 |
|---|---|---|
| `mean|action − state|` | 0.00000 | **0.07591** |
| `action[t] == state[t+1]` 精确匹配 | — | **34010/34010 (100%)** |
| 非“末尾帧”中 action≠state 的占比 | 0% | **96.6%**（其余为真实静止帧） |
| parquet 分块 / episode 指针 | — | 保持不变 |
| `meta/stats.json` action 项 | — | 已重算 |

### 5.2 修复录制根因（`widgets/camera_pyqt.py`）

将 `LeRobotRecordThread.run()` 改为**一帧延迟写入**：收到第 `t+1` 帧时才写入第 `t` 帧，
令 `action[t] = pose8[t+1]`；末帧无下一帧，`action` 沿用自身位姿（保持静止）。
总帧数不变（N 帧入 → N 帧出），观测图像与 state 仍属同一时刻。后续新录制的数据天然正确，
无需再跑离线修复脚本。

### 5.3 后续步骤

1. 用修复后的数据**重新训练**（原 checkpoint 的 normalizer 基于旧 action==state 统计，建议
   从头训练而非继续微调）。
2. 重训后用 `test_inference_episode.py` 评估，并用前述“换图像/换 state”对照实验确认模型
   已真正使用视觉（换图像时输出应有明显变化）。
3. 真机部署仍可在动作输出端叠加 Savitzky-Golay / EMA 滤波，进一步平滑 chunk 边界抖动。

## 问题 6：meta/episodes 与 data 数据行不一致（编辑中断残留）

**现象**（ela3_demo，131 episodes / meta 声称 90192 帧）：

- 对第 99 条之后的任何 episode 做修剪或删除，均报错
  `ValueError: data 中找不到 episode 99 的数据行`（`_sync_episode_data_pointers` 校验拦截）。
- 逐项核对发现三方不一致：
  - `meta/episodes` 记录 131 条（0~130），`data/*.parquet` 只有 127 条的行
    （episode_index 为 0~98、102~129，非连续）；
  - data 标签 102~129 的行数与 meta 103~130 的 length 一一对应（整体前移一位），
    即原 ep99~102 的数据行已被删除、后续标签被减 1，但 meta 未回写；
  - 其中 2 条（原 ep103、ep126）的静止帧只剪了 data 没剪视频
    （data 498→315 / 550→469 行，视频仍 498 / 550 帧），图像与 action 已错位；
  - 视频文件与 meta 完全一致（未被同步修改），并残留 6 个无数据对应的孤儿 mp4。

**根因**：`visualize_data_qwen.py` 的 `delete_episode` / `trim_episode` /
`trim_episode_ranges` / 单条任务改名共 4 处编辑函数，均采用
**先删改 data 文件、最后才回写 meta/episodes** 的顺序；操作中途异常
（一致性校验抛错、进程被杀、程序崩溃）即留下"data 已改、meta 未改"的损坏。
data 列中 `frame_index`/`timestamp` 被 `_reset_frame_columns` 规整重写正是
这些函数的特征签名。

> 注：该问题在"数据集合并后继续批量剪辑"的工作流中暴露，易被误认为合并导致。
> 经核实 `merge_lerobot_datasets.py` 是安全的：源数据集先全量加载进内存，
> 在临时目录完整构建（含一致性重建）后才原子替换目标；合并版式
> （每 episode 一个 data 文件）的数据集修剪/删除均验证正常。

**后果**：

- 所有修剪/删除操作被 `_sync_episode_data_pointers` 拦截报错（该校验阻止了
  更严重的静默损坏）；
- 若绕过校验继续编辑，meta 的 `dataset_from/to_index` 指向他集数据行，
  会造成进一步错位；
- 用于训练时 meta 引用不存在的数据行，LeRobot 加载失败或样本错位。

**修复**（2026-08-12，先完整备份至 `ela3_demo.bak_repair_<时间戳>/`）：

1. 丢弃数据行已丢失且无法恢复的 episode（原 ep99~102）及视频错位的 2 条
   （原 ep103、ep126，用户确认删除）；
2. data 的 `episode_index` 重排为连续 0~124，重写 data 分片；
3. 按 data 实际重建 `meta/episodes`（125 条）：重算 `dataset_from/to_index`、
   `length`、`stats/*/count`，保留有效视频指针，删除 12 个孤儿视频文件；
4. 重算 `meta/stats.json`、更新 `info.json`（total_episodes/total_frames/splits）；
5. 校验：每条 episode 的 meta length == data 行数 == 视频帧数，from/to 连续。

**程序加固**：

- 上述 4 处编辑函数改为**先在内存中完成 `_sync_episode_data_pointers` 校验、
  通过后才删改 data 文件**，校验失败时数据文件不再被动过，杜绝同类损坏；
- "数据集检查"按钮新增第 6 项检测（meta/data/info 三方一致性）。

## 问题 7：tasks.parquet 的 task_index 非 0 基连续（任务合并后未压实）

**现象**（ela3_demo，124 episodes / 85816 帧，2026-08-13 训练时）：

训练启动即崩溃，DataLoader worker 报：

```
IndexError: single positional indexer is out-of-bounds
  File "lerobot/datasets/dataset_reader.py", line 352, in get_item
    item["task"] = self._meta.tasks.iloc[task_idx].name
```

**根因**：`meta/tasks.parquet` 只剩 2 个任务行，但 `task_index` 列值为 **1、2**
（非 0 基连续），data 帧的 `task_index` 也是 1、2（ep0~98=1，ep99~123=2）。
lerobot 读取任务名时用 `tasks.iloc[task_idx]` **按位置**取值，`task_idx=2`
超出 2 行表的位置范围 → IndexError。

推测来源：`visualize_data_qwen.py` 的 `_batch_rename_task` 在**并入已有任务**时
`tasks_df.drop(index=old_name)` 删除了旧任务行，但没有把剩余任务的 task_index
压实为 0 基连续——当时把 `default_task`（task_index=0）并入删除后，剩余任务仍保持
1、2。`visualize_data_qt.py` 的单条改名路径无此问题（并入时不删行、新建取 max+1，
不会产生空洞）。

> 关于"是否为数据集合并导致"的核实（2026-08-13）：**不是合并脚本导致**。
> `merge_lerobot_datasets.py` 合并时会按任务名重建 0 基 task_index
> （`tasks_df = range(len(merged_tasks))`，data 按 `task_remaps` 重映射），
> 反而能**治愈** 1 基的源数据集（实测合并产物 `ela3_demo_20260811_190027`
> 为 0 基 0,1）。但合并脚本原 `remap.get(int(v), int(v))` 兜底会把 data 中
> 超出 tasks 元数据的非法 task_index 原样带入合并结果，已改为直接报错中止。
> "合并前数据集能正常修剪"不能排除本问题：修剪/删除不经过 tasks 的 iloc 查找，
> 只有训练（DataLoader 逐帧取任务名）才会触发越界。

**与问题 6 的区别**：问题 6 是 meta/episodes 与 data 数据行不一致；本问题三方行级
数据完全一致，纯粹是任务编号与行位置错位，只在 task_index 越界（≥任务数）时才暴露，
可视化工具按值查找任务名不受影响，因此此前一直未被发现。

**修复**（2026-08-13，整体减 1 压实为 0 基）：

1. `meta/tasks.parquet`：task_index 1,2 → 0,1；
2. 全部 data parquet：task_index 列减 1（行数/行序/分块布局不变）；
3. `meta/stats.json` 的 task_index 统计项（min/max/mean/q01~q99）同步减 1。

验证：修复后 `LeRobotDataset` 逐帧取任务名正常（首帧 "clear the desktop"、
末帧 "move two boxes to the yellow ares"，与 meta/episodes 一致），训练正常启动。

**程序加固**（2026-08-13）：

- `visualize_data_qwen.py` "数据集检查"新增第 7 项检测：
  - `tasks.parquet` 的 task_index 必须为 0 基连续（== `range(任务数)`）；
  - data 帧 task_index 必须落在 `[0, 任务数-1]` 且不引用不存在的编号；
  - meta/episodes 的 tasks 字符串必须都存在于 tasks.parquet。
- **根因根治**：`_batch_rename_task` 并入已有任务删除任务行后，现将剩余
  task_index 压实为 0 基连续，并同步平移 data 帧、meta/episodes 的
  task_index 列与 per-episode `stats/task_index/*` 列、全局 stats.json、
  info.json 及内存状态；
- **合并加固**：`merge_lerobot_datasets.py` 遇到 data 含 tasks 元数据之外的
  task_index 时直接报错中止，不再静默带入合并结果。

## 问题 6 / 问题 7 成因辨析（2026-08-13 补充）

两者都在"合并后批量剪辑"的工作流附近暴露，容易被归咎于数据集合并或剪辑操作。
经逐项核实，**真实成因均为可视化编辑程序（visualize_data_qwen.py）的编辑缺陷，
与数据集合并脚本无关，机制也互不相同**：

| | 问题 6 | 问题 7 |
|---|---|---|
| **一句话成因** | 剪辑/删除/改名**被中断** | 任务改名"并入已有任务"**未压实编号** |
| **元凶代码** | `delete_episode` / `trim_episode` / `trim_episode_ranges` / 单条任务改名（4 处） | `_batch_rename_task`（1 处） |
| **损坏机制** | 先改 data 文件、最后才回写 meta；中途异常留下"data 已改、meta 未改" | 删除 tasks.parquet 任务行后未把剩余 task_index 压实为 0 基连续，留空洞 |
| **损坏对象** | meta/episodes 与 data 数据行错位 | 任务编号与行位置错位（行级数据完好） |
| **暴露时机** | 下次修剪/删除时（一致性校验拦截） | 训练时（lerobot `iloc` 按位置取任务名越界） |
| **是否合并脚本导致** | 否（已核实合并脚本原子替换、安全） | 否（合并按任务名重建 0 基编号，反而可自愈） |
| **是否剪辑/删除片段导致** | **是**（中断残留） | 否（与剪辑/删除无关，从未碰 data 行结构） |

共同教训：

1. **任何"先改数据、后写元数据"的多步写入都是脆弱点**，中断即损坏；应先内存
   校验、再落盘，或临时目录构建后原子替换（合并脚本的做法）；
2. **编号类元数据（task_index/episode_index）删除行后必须压实重排**，
   并按需同步所有引用方；
3. 合并脚本在两个问题中均无责，且 2026-08-13 加固后会对非法 task_index 主动报错。

## 对后续数据采集的建议

1. 导出数据集时若做 episode 裁剪/合并，需同步重建 `meta/episodes`、`meta/stats.json`，
   并保证 `frame_index`、`timestamp` 列按 `fps` 规整（`timestamp = frame_index / fps`）。
2. `to_timestamp` 应等于 `length / fps`，与实际 mp4 时长一致。
3. 采集程序中 `task_index` 存在拼接 bug（出现 `default_taskput the black square` 任务名），建议修复。
4. `data/chunk-000/file-066.parquet.corrupted` 为损坏文件（已被 visualize_data_qt.py 重命名），可删除。
5. **action 标签**：`action` 必须是“下一步目标位姿”，不能等于当前 `observation.state`。
   `camera_pyqt.py` 已改为一帧延迟写入（`action[t]=pose8[t+1]`）。若新增其它录制入口，
   务必遵循同一约定，否则模型会退化为忽略视觉的恒等映射（见问题 5）。
6. 旧数据集（本文件之前录制的所有 episode）均存在 action==state 问题，需用
   `fix_action_labels.py` 修复后方可用于训练。
7. **编辑操作中断风险**：删除/剪辑/改名类操作若中途报错或程序被强杀，可能留下
   meta 与 data 不一致（问题 6）。修剪/删除前建议先用"数据集检查"第 6 项确认
   三方一致；一旦发现不一致，停止编辑并从最近备份恢复或按问题 6 的修复流程重建。
8. **任务合并风险**：批量任务改名"并入已有任务"会删除 tasks.parquet 中的任务行；
   旧版程序不压实 task_index 会产生空洞（问题 7），已于 2026-08-13 根治。
   训练前若报 `single positional indexer is out-of-bounds`，即本问题，按问题 7 修复。
9. **编辑加固（2026-08-22，第二轮）**：第一轮加固（先校验后动笔）只保证"新 meta 与新
   data 自洽"，但在已损坏数据集上 `_sync_episode_data_pointers` 不校验 length/区间，
   旧 meta 的绝对区间会在带病 data 上切错行并静默写出"自洽但错误"的结果。本轮修复：
   - 新增编辑前置闸门 `check_dataset_consistency` / `_assert_dataset_consistent`
     （meta length == data 行数、from/to 连续且末尾==总行数、info total_frames/
     total_episodes 吻合）：`delete_episode`/`delete_episodes`/`trim_episode`/
     `trim_episode_ranges`/`denoise_dataset`/`_save_task_name`/`_batch_rename_task`
     动笔前一律先过闸门，不一致直接拒绝编辑；
   - `_save_task_name` 重构：全部内容内存就绪并校验后才动笔；只重写含目标
     episode 行的 data 文件（行数/布局不变，指针保持有效，不再整集重写）；
     修改文件先备份到 `.bak_task_save_<时间戳>/`；
   - `delete_episode`/`delete_episodes` 新增 `backup_enabled`（GUI 复用
     "剪辑前自动备份"复选框），备份复用 `_backup_for_trim`；
   - parquet 写入全面原子化（tmp + os.replace）：`_atomic_write_parquet` 应用于
     `_write_parquet_chunks`、`_save_task_name`、`_batch_rename_task`、
     `denoise_dataset`、`write_language_to_dataset`（后者另增全量 data 备份
     `.bak_language_<时间戳>/`）；tasks.parquet 因以任务名为索引单独用
     tmp+os.replace 原子写。
10. **孤儿任务回收（2026-08-22 补充）**：`delete_episode`/`delete_episodes` 原实现
    删除 episode 后不更新 tasks.parquet 与 info.json 的 total_tasks，被带走最后一处
    引用的任务（如录制端拼接 bug 产生的 default_task）残留为孤儿行。孤儿行本身
    不影响训练读取（task_index 编号未动、行位置仍对齐），但若被直接删行而不压实
    会触发问题 7 式越界。现已加入 `_gc_orphan_tasks`：删除流程自动回收孤儿任务行、
    task_index 压实为 0 基连续，并同步平移 data 帧、meta/episodes 的 task_index 列
    与 per-episode stats/task_index/* 列、info.json total_tasks（`_save_task_name`
    新增任务行时也同步 total_tasks）；`_backup_for_trim` 的 meta 备份清单补充
    tasks.parquet。
11. **tasks.parquet 巡检工具（2026-08-22）**：`visualize_data_qwen.py` 信息总揽新增
    tasks.parquet 健康段（total_tasks 一致性 / task_index 0 基连续 / 引用越界 /
    孤儿任务 / 任务名存在性，孤儿任务标红提示）；新增独立 CLI 工具
    `check_tasks_parquet.py`（纯 pandas 依赖）：
    `python check_tasks_parquet.py [数据集或根目录] [--fix] [--no-backup]`，
    默认扫描 ./lerobot_data 全部数据集；--fix 删除孤儿任务并把 task_index 压实为
    0 基连续（同步平移 data、meta/episodes 的 task_index 与 stats/task_index/*
    统计列、info.json total_tasks、stats.json task_index 项），修改文件备份到
    `.bak_tasks_fix_<时间戳>/`，全部 parquet 原子写；引用不存在编号时拒绝自动修复。
    注意 v3.0 的 meta/episodes 无 task_index 列，episode→任务关联经 tasks 名称列换算。
