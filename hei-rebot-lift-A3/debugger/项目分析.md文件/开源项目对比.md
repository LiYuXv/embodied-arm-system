# 开源项目对比：so101-real (LeRobot 0.6) vs 本项目 (ela3)

> 分析对象：`debugger/so101-real-main/lerobot-0.6`（GitHub: JereoZero/so101-real，
> SO-101 双臂 SmolVLA 真机项目，**最终成功率 21/25 = 84%**）。
> 目的：对照其数据采集/训练/部署做法，找出我们真机"基本无法成功"的可迁移改进点。
> 本文档结论与 `smolVLA模型训练主要要点.md` 互为补充。

---

## 1. 对方成绩单

| 项 | 值 |
|---|---|
| 机器人 | SO-101 单臂（leader-follower 主从遥操作） |
| 模型 | SmolVLA（500M VLM） |
| 数据 | **199 条 / 52,010 帧**（20 个版本迭代合并） |
| 训练 | **40,000 步 × batch 36 ≈ 27.7 epoch**，use_amp |
| 成功率 | **21/25 = 84%**（抓葡萄块放盘子） |

## 2. 数据采集对比（核心差异）

| 维度 | so101-real | 我们 (camera_pyqt.py) | 影响分析 |
|---|---|---|---|
| **action/state 空间** | **6 维关节角（度）**，action=从臂**实际执行**的关节目标 | **7 维末端位姿**（x,y,z,rx,ry,rz,gripper 弧度），action=未来 N 帧位姿 | **最大差异**，见 §3.1 |
| 相机分辨率 | **640×480** | 1280×720 | 模型输入都 letterbox 到 512 宽：对方有效 512×**384**，我们 512×**288**——**对方有效像素多 33%** |
| 帧率 | **30 fps**（采集/训练/控制统一） | 20 fps | 我们动作粒度更粗 |
| 遥操作方式 | **leader-follower 主从物理联动**（零延迟、天然平滑） | VR 遥操作 | VR 有延迟/抖动，示教质量依赖操作者经验 |
| 关节精简 | **fixed_joints 固定 wrist_roll**（不学该关节） | 7 维全学（rx/ry/rz 欧拉角） | 对方降低学习维度；欧拉角还有绕圈/万向节奇异风险 |
| episode 时长 | 60s 上限，失误按左箭头当场重录 | 手动开始/停止 | 对方的"当场重录"减少脏数据流入 |
| 数据质检流程 | 录完即 `check_data.py` + `replay.py` **回放验证后才训练** | 有"数据集检查"（7 项） | 对等，我们的检查更偏元数据一致性 |
| 任务文本 | 单任务一句英文 | 同 | 一致 |

### 2.1 对方录制的一个关键 patch（与我们问题 5 同源）

lerobot 0.6 原版录制把**主臂原始指令**写入 action；本项目打了 patch 8b，
改写**从臂实际执行的动作**（含 fixed_joints 覆盖）——即"数据集里存的 action
必须是机器人真实走过的动作"。这与我们问题 5 修复（action=下一帧**反馈位姿**）
是同一原则：**train/execution 分布一致性**。

## 3. 为什么他们成功、我们不成功（根因对照）

### 3.1 关节空间 vs 末端位姿空间（最关键）

| | 关节空间（对方） | 末端位姿（我们） |
|---|---|---|
| 执行链路 | 模型输出 → 关节 PD 直驱 | 模型输出 → **IK 逆解** → 关节 PD |
| 一致性 | 录制值=执行值，零转换损耗 | FK 录制 → IK 执行，**往返误差+奇异位形风险** |
| 学习难度 | 6 维连续量 | 7 维含欧拉角（**rx/ry/rz 有 ±π 跳变**） |
| 控制带宽 | 直接 | 受 IK 数值稳定性约束 |

欧拉角在示教经过奇异姿态附近时会出现 ±π 跳变，这些样本对回归模型是
"在同一 state 下标签相差 2π"的坏样本——会显著增加输出方差，可能正是
我们 chunk 摆动的放大器之一（待验证：检查数据中 rx/ry/rz 是否有跳变点）。

### 3.2 ~~时间上下文：n_obs_steps=4~~（已证伪，见 §9.3）

对方命令里确实传了 `--policy.n_obs_steps=4`，但**该参数对 SmolVLA 无效**
（lerobot 0.4.4/0.6.x 的 `SmolVLAConfig.observation_delta_indices` 硬编码 `[0]`，
modeling 代码完全不读 n_obs_steps）——对方实际也是单帧观测。
此因素从成功原因中剔除。

### 3.3 训练量

对方 27.7 epoch vs 我们 3.5 epoch（**8 倍差距**）。

### 3.4 数据量与迭代方式

对方 199 条分 20 个版本迭代（每版录完回放验证、不好就重录）；
我们 124 条两个任务（96:24 不平衡）。

### 3.5 部署

对方 `lerobot-rollout --inference.type=rtc`（RTC 是官方推荐路径）+ 30Hz 控制；
我们自研 RTC 执行器 + 20Hz + 低通/采样平均（功能对等，参数不同：
对方 n_action_steps=10 比我们的 20 更保守，陈旧动作更少）。

### 3.6 硬件细节

对方把夹爪扭矩调到 100%（硬件级抓取可靠性）；
我们的力矩是**模型输入特征**（更高级用法，对方没有）。

## 4. 可迁移改进清单（按预期收益排序）

| 优先级 | 改进 | 依据 |
|---|---|---|
| ~~★★★~~ | ~~`n_obs_steps: 4`~~ **已证伪**（对 SmolVLA 无效，§9.3） | — |
| ★★★ | **检查数据中欧拉角 ±π 跳变**；考虑 rx/ry 固定（任务若姿态基本竖直，把 rx,ry 设为常量写入 fixed 列，只学 z 旋转） | §3.1 |
| ★★★ | **步数 18K→40K**、数据补录到各 50+/任务 | §3.3/3.4 |
| ★★ | **改用关节空间 action**（长期方向）：采集 joints 作为 state/action（SDK 有 joint_states 反馈），推理输出关节目标直接下发，绕开 IK | §3.1，改动大但根除一类误差 |
| ★★ | 采集帧率 20→**30fps**（与控制频率统一） | §2 |

| ★ | 相机保持 1280×720 即可；若想对齐对方有效分辨率，可采集时**裁切为 960×720**（4:3，letterbox 后 512×384） | §2 |
| ★ | 录制工作流加"当场重录"（录坏即弃） | §2 |
| ★ | n_action_steps 20→10（RTC 下减少陈旧动作） | §3.5 |

## 5. 我们独有、对方没有的优势

- **力矩输入**（observation.gripper_torque）：消融实测提升 11~20%，接触阶段的关键感知
- **更完整的诊断链**：7 项数据集检查、推理一次（含 executed.csv 目标vs反馈）、
  摄像头/力矩消融、采样平均、lookahead 估计
- 自研 RTC 执行器（软融合+延迟补偿+限幅+EMA）

## 6. 下一步建议的实验顺序

1. steps 40K，用 lookahead=5 数据重训（n_obs_steps 已证无效，不设）
2. 离线验收：chunk 路径/净位移 <2（当前 4.3）
3. "推理一次"真机：反馈能跟踪到终点（跟踪误差 <10mm）
4. 仍不达标再评估关节空间改造（★★ 项）

## 8. 附：相机分辨率与 letterbox 有效像素分析

SmolVLA 输入固定为 512×512（`resize_imgs_with_padding`），处理方式是
**等比缩放 + 补黑边（letterbox，非拉伸）**。有效内容像素取决于采集长宽比：

| 采集分辨率 | 缩放比 | 有效画面 | 有效像素 | 画布利用率 |
|---|---|---|---|---|
| 对方 640×480（4:3） | 1.25 | 512×**384** | 196,608 | **75%** |
| 我们 1280×720（16:9） | 2.5 | 512×**288** | 147,456 | 56% |
| 720×720 中心裁切（1:1） | 1.41 | 512×**512** 满幅 | 262,144 | **100%（+78%）** |
| 960×720（4:3） | 1.875 | 512×384 | 196,608 | 75%（+33%） |

**能否直接录 512×512？** 不能靠硬件：USB 摄像头（UVC）只有离散原生档位
（实测本机 video0：640×480 / 800×600 / 1280×720 / 1920×1080…，**无 512×512**）。
只能软件处理。本程序"LeRobot图像"下拉已提供 **720×720（中心裁切）** 选项：
`_resize_frame` 在长宽比不一致时**先中心裁切再缩放**（1280×720 → 取中央
720×720 → 无失真），录制与推理共用同一函数保证一致。
（旧版的 480×480/256×256 选项是直接拉伸失真，已移除。）

选型建议（视野 vs 像素密度权衡）：

1. 在可视化/预览中检查 720×720 方框是否覆盖全部任务关键区（抓取点、放置区、
   机械臂活动范围）：覆盖 → 用 720×720 裁切（收益最大）；有超出 → 用 960×720
   折中；物体常出现在两侧 → 维持 1280×720（看不到比看不清更致命）
2. **长宽比是 train/serve 一致性参数**：改比例后必须用新比例重录并重训，
   推理端 `_lerobot_image_size` 同步修改，新旧数据不可混训
3. 不要调大 `resize_imgs_with_padding`（如 [720,1280]）：VLM token 数翻倍，
   推理显著变慢，得不偿失

## 9. 训练超参数对比（train.py + docs/05 vs train_model.py + smolvla_omy.yaml）

两边入口相同（均为 `lerobot.scripts.lerobot_train.main` 薄封装），差异全部在配置：

| 超参数 | so101-real（84% 成功） | 我们（smolvla_omy.yaml） | 评价 |
|---|---|---|---|
| **预训练起点** | `--policy.path=smolvla_base_migrated`（**完整 SmolVLA 预训练**：VLM + 动作专家在 OpenX 机器人数据上预训过） | `pretrained_path: None`，仅加载 SmolVLM2 纯视觉语言骨干，**动作专家从零训练** | **最大差距**，见 §9.1 |
| steps × batch | 40,000 × 36 ≈ **27.7 epoch**（52K 帧） | 18,000 × 16 ≈ **3.5 epoch**（86K 帧） | 8 倍训练量差距 |
| **n_obs_steps** | 4（**实际无效**，§9.3） | 1 | 双方都是单帧观测 |
| use_amp | **true**（bf16 省显存加速） | false | 开启后可上更大 batch |
| batch_size | 36（12GB 显存 + amp） | 16 | 开 amp 后可试 24~32 |
| image_transforms | **enable=true + random_order=true** | enable=false | 小数据泛化必需 |
| eval_split | **0.1**（10% 验证 loss） | 0（无验证集） | 无法监控过拟合 |
| chunk_size / n_action_steps | 50 / **10** | 40 / 20 | 对方执行更短的新鲜动作段 |
| video_backend | **pyav**（torchcodec 在其环境不兼容） | torchcodec（我们环境正常） | 无需改 |
| lr / 调度 | 默认 1e-4 | 1e-4 cosine（preset 接管） | 一致 |
| 相机键名 | 需 rename_map front/top→camera1/camera2 | 我们的 cam1/cam2 直用（**但若加载 smolvla_base 需 rename_map cam1→camera1**） | 见 §9.1 |
| 工作流 | 分阶段续训（10k→20k→30k，每段先测再续）；录完先 replay 验证 | 单次训练 | 对方"每 10k 步先推理再决定"值得借鉴 |

### 9.1 最关键差距：预训练起点

对方从 `lerobot/smolvla_base`（**在机器人数据上预训练过的完整 SmolVLA**，
VLM + action expert 均有动作先验）微调；我们只加载 SmolVLM2 视觉语言骨干
（`vlm_model_name=./pretrained_models/smolvlm2-500m-video-instruct`），
**action expert 是从零随机初始化学的**——这解释了为什么他们 20K 步即收敛稳定，
而我们 18K 步输出摆动大。

**行动项**：下载 `lerobot/smolvla_base` 并迁移后作为 `policy.pretrained_path`
（HF 不可达时用 hf-mirror），同时：
- 加 `rename_map`：`observation.images.cam1→camera1`、`cam2→camera2`
  （smolvla_base 预训练时相机键名是 camera1/camera2）
- `load_vlm_weights` 保持 false，预训练权重内含 VLM
- 力矩维度是我们自定义扩展（预训练模型无此输入），需确认
  `smolvla_torque` 的 state_proj 对 8 维输入是新增初始化还是复用——
  从零初始化的只有力矩那 1 维的投影权重，其余仍继承预训练，收益仍在

### 9.2 建议的新训练配置（按对方参数对齐）

```yaml
policy:
  pretrained_path: ./pretrained_models/smolvla_base_migrated   # 需先下载迁移
  # n_obs_steps 不要设——对 SmolVLA 无效（§9.3）
  chunk_size: 50          # 与 smolvla_base 预训练一致（可选）
  n_action_steps: 10      # 减少陈旧动作
dataset:
  image_transforms:
    enable: true
    random_order: true
  eval_split: 0.1
steps: 40_000
batch_size: 24            # 先开 use_amp 再试 24~32（OOM 降回 16）
```

配合分阶段续训流程：10K 步测一次（离线 + 推理一次），达标即停——
对方 20K 步达标后第三阶段就没再训。

### 9.3 勘误：`n_obs_steps` 对 SmolVLA 无效（2026-08-15 实测）

lerobot 0.4.4 与 0.6.1 的 `SmolVLAConfig.observation_delta_indices` 均硬编码
`[0]`（configuration_smolvla.py），modeling_smolvla.py 完全不读 `n_obs_steps`。
实测设置 `n_obs_steps: 4` 后数据集的观测 delta_timestamps 仍为 `[0.0]`、
state 形状 `[1,7]`——**观测历史从未生效**。对方项目命令中的
`--policy.n_obs_steps=4` 也是空操作，其成功应归因于：smolvla_base 预训练起点、
27.7 epoch、关节空间直驱、主从联动示教质量。本文 §3.2/§4/§7 相关表述已更正。

## 7. 附：录制数据的 lookahead 等效对比

对方录制循环（`lerobot_record.py:289-336`，30fps）每个周期：
`state[t]=从臂反馈 → action[t]=主臂当前关节角 → send_action 下发（从臂下一周期到达）`。

**对方的等效 lookahead ≈ 1 帧 @30fps（33ms）**，即 action[t]≈state[t+1]，
几乎没有前瞻（比我们旧版的 1 帧 @20fps=50ms 提前量更小）。

他们 lookahead≈1 仍能成功的支撑条件（与我们对照）：

| 因素 | so101-real | 我们 |
|---|---|---|
| 动作空间 | 关节角直驱（目标=反馈同源同设备，一周期内必达） | 末端位姿 + IK（往返误差、欧拉角 ±π 跳变） |
| 方向信息来源 | ~~n_obs_steps=4~~（已证无效，双方同为单帧观测） | 靠 lookahead 标签补偿 |
| 训练量 | 27.7 epoch（采样方差小） | 3.5 epoch |
| 示教平滑度 | 主从物理联动天然平滑 | VR 遥操作有延迟抖动 |

**要点**：给模型"方向感"的途径中，n_obs_steps（观测历史）对 SmolVLA 无效；
**lookahead 是当前唯一可用的方向感来源**（放进标签，逼模型预判 0.25s 后）。
对方没有lookahead 也成功，靠的是关节空间直驱 + 预训练起点 + 训练量。

实践建议：重训用 lookahead=5；若摆动比降到 ~1.5 且真机流畅，可尝试降回
1~2 提升精细度；若将来改关节空间 action，lookahead 可像对方一样回到 1。
